Storage vs Compute: the great divorce

The single architectural decision that makes the modern data stack cheap to start, easy to scale, and billed by usage instead of hardware.

Mario Zamudio · June 2026 · 3 min read · From LinkedIn

Legacy on-prem systems combined storage and compute in a single box. To run bigger queries you bought bigger hardware — and that hardware sat there, billing you, even when it was idle. Modern cloud platforms split the two into independent services: data lives in affordable object storage, and compute engines activate only when a query actually runs.

Idle = $0 compute. Scale up for five minutes, then scale back down.

You pay for use, not capacity

Spin an engine up to crunch a heavy job, then shut it down. Because you are billed for the seconds the engine runs rather than for hardware you own, cost tracks usage instead of peak provisioning — a structural change from the always-on model.

One copy, many consumers

With storage decoupled from compute, several teams and engines can read the same dataset at the same time without duplicating it. No more copying data into each team's warehouse just so they can query it.

The same pattern, everywhere

This separation shows up in Snowflake, Databricks, BigQuery, and Microsoft Fabric. The product names and buttons differ, but the underlying decision is identical. Learn the pattern, not the product — and read the full deep-dive in Learn the Pattern, Part 2.
